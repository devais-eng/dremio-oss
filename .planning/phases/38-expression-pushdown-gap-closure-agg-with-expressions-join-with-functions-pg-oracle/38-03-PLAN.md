## Root Cause

When a `LogicalProject` with function expressions (e.g. `CAST(col AS type)`) sits between the `LogicalJoin` and the `JdbcScanDrel`, `join.getLeft().getRowType()` (or `join.getRight().getRowType()`) returns a row type with **synthetic field names** like `EXPR$0` instead of the original scan column names. The `deriveColumnsFromRowType()` method captures these synthetic names and passes them as `leftProjectedCols`/`rightProjectedCols` to `JdbcJoinScanDrel`. Later, `JdbcJoinScanPrel.getPhysicalOperator()` uses these synthetic names to build the SQL `SELECT` list and `ON` clause column mappings — resulting in either:
- **Oracle**: `ORA-00904` errors because column aliases like `DEPARTMENT0` (Calcite dedup suffix on `EXPR$0`) don't exist in the table.
- **PostgreSQL**: Silently wrong behavior (CAST(VARCHAR AS VARCHAR) is optimized away, masking the bug).

## Fix

In `onMatch()`, **detect when an intermediate `LogicalProject` with non-trivial expressions exists** using the existing `hasNonTrivialProject()` helper. When detected, derive projected column names from the **underlying scan's row type** (via `findJdbcScan()`) instead of from the join input's row type.

### Changes to `JdbcPushJoinIntoScan.onMatch()`:

**Before** (current lines 151-152):
```java
List<SchemaPath> leftProjectedCols = deriveColumnsFromRowType(join.getLeft().getRowType());
List<SchemaPath> rightProjectedCols = deriveColumnsFromRowType(join.getRight().getRowType());
```

**After:**
```java
// When an intermediate LogicalProject with function expressions (e.g. CAST) exists
// between the join and the scan, the join input row type has synthetic names (EXPR$0,
// EXPR$1) that do not correspond to actual table columns. In that case, derive the
// projected columns from the scan's row type (which has the real column names).
//
// The hasNonTrivialProject() helper detects intermediate projects with non-RexInputRef
// expressions. When present, we use the scan's row type for column derivation.
// When absent (pure column renames or no project at all), the join input row type is
// correct and we use it as before — it includes extra columns needed for WHERE filters
// above the join (see existing comment about leftScan.getProjectedColumns() pitfall).
List<SchemaPath> leftProjectedCols;
if (hasNonTrivialProject(join.getLeft())) {
  leftProjectedCols = deriveColumnsFromRowType(leftScan.getRowType());
} else {
  leftProjectedCols = deriveColumnsFromRowType(join.getLeft().getRowType());
}

List<SchemaPath> rightProjectedCols;
if (hasNonTrivialProject(join.getRight())) {
  rightProjectedCols = deriveColumnsFromRowType(rightScan.getRowType());
} else {
  rightProjectedCols = deriveColumnsFromRowType(join.getRight().getRowType());
}
```

**IMPORTANT**: The `leftInputRowType` and `rightInputRowType` passed to `JdbcJoinScanDrel` (lines 205-206) must STAY as `join.getLeft().getRowType()` and `join.getRight().getRowType()` — these are needed for `conditionRex` RexInputRef index alignment in `JdbcJoinScanPrel.getPhysicalOperator()`. Only the `leftProjectedCols`/`rightProjectedCols` (used for SQL SELECT list column names) need the fix.
