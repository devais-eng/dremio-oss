<objective>
Define the SupportsBranchAwareRestCatalog interface, implement it conditionally on RestIcebergCatalogPlugin, expand the CatalogUtil AT specifier gate, and extend plan cache exclusion for branch-aware sources.

Purpose: This plan creates the interface and wiring infrastructure that CatalogImpl needs to dispatch AT BRANCH queries to Nessie-enabled RESTCATALOG sources. Without these changes, AT BRANCH queries on RESTCATALOG sources throw "Source does not support AT BRANCH/TAG/COMMIT" and the plan cache could serve stale cross-branch results.

Output: New SupportsBranchAwareRestCatalog interface, conditional implementation on RestIcebergCatalogPlugin, expanded CatalogUtil gate, and plan cache safety.
</objective>

**1. Create `SupportsBranchAwareRestCatalog.java`** in `sabot/kernel/src/main/java/com/dremio/exec/catalog/`:

```java
package com.dremio.exec.catalog;
```

Define a public interface `SupportsBranchAwareRestCatalog extends com.dremio.common.Wrapper` with exactly 3 methods:
- `ResolvedVersionContext resolveVersionContext(VersionContext versionContext)` -- lightweight resolution, no server round-trip
- `CatalogAccessor getCatalogAccessorForBranch(String branchName)` -- returns cached branch-scoped accessor (from Phase 22)
- `String getDefaultBranch()` -- returns server-defined default branch name

Import `com.dremio.catalog.model.ResolvedVersionContext`, `com.dremio.catalog.model.VersionContext`, and `com.dremio.plugins.icebergcatalog.store.CatalogAccessor`.

IMPORTANT: `CatalogAccessor` lives in the `icebergcatalog` plugin module, but the interface is in `sabot/kernel`. This creates a module dependency issue. To avoid adding a circular dependency from kernel to plugin, the `getCatalogAccessorForBranch` method should NOT reference `CatalogAccessor` directly. Instead, use the `StoragePlugin` approach: the return type should be `Object` and the caller (CatalogImpl) casts as needed.

ACTUALLY -- re-read the codebase: `CatalogImpl` does not call `getCatalogAccessorForBranch` directly. The entire flow in `getTableSnapshotForBranchAwareRestSource()` (Plan 02) will unwrap the plugin to `SupportsBranchAwareRestCatalog` and call the method, but needs to then call `getDatasetHandle` on the accessor. The simplest approach: define the return type as `Object` in the interface, OR keep it generic. Since the caller knows it returns a `CatalogAccessor`, it will cast.

BETTER APPROACH: Look at how existing code handles this. The `IcebergCatalogPlugin.getDatasetHandle(EntityPath)` at line 179-187 calls `getCatalogAccessor().getDatasetHandle(components, this, options)`. The `CatalogImpl.getTableSnapshotForBranchAwareRestSource()` in Plan 02 needs to load a table through a branch-scoped accessor. The simplest path that avoids module dependency issues: make the `getCatalogAccessorForBranch` return type `Object` in the kernel-level interface definition, and have the implementation in RestIcebergCatalogPlugin return the actual CatalogAccessor. The caller in CatalogImpl (Plan 02) will cast.

SIMPLEST: Since `getDatasetHandle(EntityPath)` is on `StoragePlugin` (in kernel module), not on `CatalogAccessor`, the Plan 02 method will NOT call accessor methods directly from CatalogImpl. Instead it will provide the branch name and let the plugin load the table internally. So we do NOT need CatalogAccessor in the interface return type at all. We can just have `void` or remove that method from the interface.

HOWEVER, per the research and architecture decision, `getCatalogAccessorForBranch(String)` is one of the 3 interface methods. The actual usage pattern in Plan 02 is: unwrap to SupportsBranchAwareRestCatalog, get branch accessor, call accessor.getDatasetHandle(). This means Plan 02's new CatalogImpl method will need to interact with the accessor.

FINAL DECISION: Since `CatalogAccessor` is a plugin-level interface, use `Object` as the return type in the kernel-level interface definition for `getCatalogAccessorForBranch`. Add a Javadoc noting it returns a CatalogAccessor (for documentation). The caller in CatalogImpl (Plan 02) will NOT call methods on the accessor directly -- instead, the flow will go through the plugin's getDatasetHandle. See Plan 02 for the full approach.

WAIT -- re-examine the architecture. The key insight from research Pitfall 3: "The new method in CatalogImpl should NOT go through ManagedStoragePlugin.getDatasetHandle(). Instead, it should call plugin.unwrap(SupportsBranchAwareRestCatalog.class).getCatalogAccessorForBranch(branchName), then accessor.getDatasetHandle(components, plugin, options) directly."

But this requires CatalogImpl (kernel module) to call methods on CatalogAccessor (plugin module), which is a dependency violation.

ACTUAL SOLUTION: Add a method to the interface that takes the full load path: `Optional<DatasetHandle> getDatasetHandleForBranch(String branchName, EntityPath datasetPath, GetDatasetOption... options)`. This encapsulates the branch-scoped table loading entirely within the plugin. CatalogImpl calls this single method instead of separately getting the accessor and calling getDatasetHandle on it.

REVISED interface (3 methods):
- `ResolvedVersionContext resolveVersionContext(VersionContext versionContext)`
- `Optional<DatasetHandle> getDatasetHandleForBranch(String branchName, EntityPath datasetPath, GetDatasetOption... options)` -- encapsulates branch accessor + table load
- `String getDefaultBranch()`

This avoids all module dependency issues. Types used: `ResolvedVersionContext` (services/catalog), `VersionContext` (services/catalog), `DatasetHandle` (connector), `EntityPath` (connector), `GetDatasetOption` (connector) -- all available in kernel module.

Add Dremio license header. Add Javadoc explaining this is a narrow interface for branch-aware REST catalog access (not full VersionedPlugin).

**1. Modify `CatalogUtil.java`**:

Add a new static helper method `requestedPluginSupportsBranchAwareRest(String sourceName, SourceCatalog catalog)`:
```java
@Deprecated(since = "Catalog should be the only one running this business logic", forRemoval = true)
public static boolean requestedPluginSupportsBranchAwareRest(String sourceName, SourceCatalog catalog) {
    try {
        return catalog.getSource(sourceName) != null
            && catalog.getSource(sourceName).isWrapperFor(SupportsBranchAwareRestCatalog.class);
    } catch (UserException ignored) {
        return false;
    }
}
```
Mark it `@Deprecated` with the same annotation as `requestedPluginSupportsVersionedTables` -- this follows the existing pattern where Catalog itself should handle this check eventually.

Modify `forATSpecifierAccess()` (line 285-291) to also check for branch-aware REST sources:
```java
public static boolean forATSpecifierAccess(CatalogEntityKey catalogEntityKey, SourceCatalog catalog) {
    boolean isVersionedTable =
        requestedPluginSupportsVersionedTables(catalogEntityKey.getRootEntity(), catalog);
    boolean isBranchAwareRestCatalog =
        requestedPluginSupportsBranchAwareRest(catalogEntityKey.getRootEntity(), catalog);
    return ((catalogEntityKey.hasTableVersionContext())
        && (isVersionedTable || isBranchAwareRestCatalog
            || catalogEntityKey.getTableVersionContext().isTimeTravelType()));
}
```

This is CRITICAL (Pitfall 1 from research): without this change, `CatalogImpl.getTable(CatalogEntityKey)` with AT BRANCH on a Nessie-enabled RESTCATALOG source falls through to `getTable(NamespaceKey)`, silently ignoring the version context and returning default branch data.

Add import: `com.dremio.exec.catalog.SupportsBranchAwareRestCatalog`.

**2. Modify `PlanCacheUtils.java`**:

Modify `checkForVersionedTable()` (line 307-321) to also check for branch-aware REST sources:
```java
private static boolean checkForVersionedTable(SqlHandlerConfig sqlHandlerConfig) {
    PlannerCatalog plannerCatalog = sqlHandlerConfig.getConverter().getPlannerCatalog();
    Catalog catalog = sqlHandlerConfig.getContext().getCatalog();
    for (DremioTable table : plannerCatalog.getAllRequestedTables()) {
        if (CatalogUtil.requestedPluginSupportsVersionedTables(table.getPath(), catalog)
            || CatalogUtil.requestedPluginSupportsBranchAwareRest(
                table.getPath().getRoot(), catalog)) {
            return true;
        }
    }
    return false;
}
```

This reuses the existing `NOT_PUT_VERSIONED_TABLE` event constant -- both versioned and branch-aware REST sources are excluded from plan cache for the same reason (no reliable mtime-based validation).

Adding a separate check is cleaner and preserves semantic clarity. The research suggested Option A (extending the existing method) but this would conflate two distinct concepts. Option B (separate method + check in PlanCacheUtils) is better for maintainability.
