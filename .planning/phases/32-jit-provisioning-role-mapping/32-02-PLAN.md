Create `JitUserProvisioner` in `services/keycloak` package:

```java
public class JitUserProvisioner {
  private final Supplier<LegacyIndexedStore<UID, UserInfo>> userStore;

  public JitUserProvisioner(Provider<LegacyKVStoreProvider> kvStoreProvider) {
    this.userStore = Suppliers.memoize(
        () -> kvStoreProvider.get().getStore(SimpleUserService.UserGroupStoreBuilder.class));
  }

  /**
   * Creates a REMOTE (locked) user for the given Keycloak identity.
   * Idempotent: if the user already exists (concurrent race or repeat call), silently succeeds.
   */
  public void provision(String username, String email) throws IOException {
    UID uid = new UID(UUID.randomUUID().toString());
    UserConfig config = new UserConfig()
        .setUid(uid)
        .setUserName(username)
        .setEmail(email != null ? email : "")
        .setType(UserType.REMOTE)
        .setCreatedAt(System.currentTimeMillis())
        .setModifiedAt(System.currentTimeMillis())
        .setActive(true);
    UserInfo info = new UserInfo().setConfig(config);
    try {
      userStore.get().put(uid, info);
    } catch (Exception e) {
      // JIT-03: concurrent creation race -- if user now exists, that's fine
      // Log at debug and return. The caller will re-fetch the user via getUser().
      logger.debug("JIT provisioning race for user '{}': {}", username, e.getMessage());
    }
  }
}
```

**Testing approach:** Use a mock `LegacyKVStoreProvider` and mock `LegacyIndexedStore<UID, UserInfo>` via Mockito. Capture the `put()` call arguments to verify UserConfig fields. For the idempotency test, make the mock's `put()` throw on second call and verify no exception propagates.

**CRITICAL - Anti-pattern awareness per Research Pitfall 5:** Do NOT use `SimpleUserService.createUser()` -- it calls `validatePassword()` and does not set `UserType.REMOTE`. Build `UserConfig` directly and write to the store.

**CRITICAL - Anti-pattern awareness per Research Pitfall 6:** For single-coordinator deployments, the TOCTOU gap in `put()` without `PutOption.CREATE` is acceptable. The `findUserByUserName()` check before create would add unnecessary complexity. The exception catch handles the concurrent race.

Note on store put() behavior: `LegacyIndexedStore.put(key, value)` without PutOption is a last-write-wins upsert. Two concurrent provisions with different UIDs will both succeed but the second overwrites the first. Since both create the same username with REMOTE type, this is acceptable -- the last-written UID becomes the canonical record. The caller (DACAuthFilter) immediately calls `getUser(username)` after provision, which reads by index (username), so it always gets the current record regardless of which UID won.
