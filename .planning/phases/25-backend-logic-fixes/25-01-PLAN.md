  <name>Task 1: Compute RBAC-aware dataset count in SpaceResource (LOGIC-01)</name>
  <files>dac/backend/src/main/java/com/dremio/dac/resource/SpaceResource.java</files>
  <action>
In SpaceResource.getSpace(), the dataset count is computed BEFORE RBAC filtering via `namespaceService.getDatasetCount()` (line 114-120). This returns the total count of ALL datasets, not just the ones visible to the current user.

Fix: When RBAC is enabled and the user is not admin, compute the dataset count from the RBAC-filtered children list instead of using `namespaceService.getDatasetCount()`.

Modify the `getSpace()` method:
1. Always fetch the children list (move `namespaceService.list()` before the count computation, regardless of `includeContents`).
2. Apply `filterByRbacVisibility(children)` to the children list.
3. Count only DATASET-type entries in the filtered list to get the RBAC-aware dataset count.
4. When RBAC is disabled or user is admin, keep using `namespaceService.getDatasetCount()` for the optimized path.

Implementation pattern:
```java
// Inside getSpace():
SpaceConfig config = namespaceService.getSpace(spacePath.toNamespaceKey());
List<NameSpaceContainer> children = namespaceService.list(spacePath.toNamespaceKey(), null, Integer.MAX_VALUE);
children = filterByRbacVisibility(children);

int datasetCount;
if (rbacService == null || dremioConfig == null
    || !dremioConfig.getBoolean(DremioConfig.RBAC_ENABLED)
    || rbacService.isAdminMember(securityContext.getUserPrincipal().getName())) {
  // Optimized path: use namespace count for admin/RBAC-off
  datasetCount = namespaceService.getDatasetCount(
      spacePath.toNamespaceKey(),
      BoundedDatasetCount.SEARCH_TIME_LIMIT_MS,
      BoundedDatasetCount.COUNT_LIMIT_TO_STOP_SEARCH).getCount();
} else {
  // RBAC-aware path: count datasets from filtered children
  datasetCount = (int) children.stream()
      .filter(c -> c.getType() == NameSpaceContainer.Type.DATASET)
      .count();
}

NamespaceTree contents = null;
if (includeContents) {
  contents = newNamespaceTree(children);
}
return newSpace(config, contents, datasetCount);
```

Note: The children are always fetched now (not just when `includeContents` is true). This is acceptable because the RBAC filtering already requires the children list, and the `includeContents=false` path is only used by the sidebar summary which also needs the correct count. For admin users, the optimized `getDatasetCount()` path is still used.

Do NOT modify `filterByRbacVisibility()` -- it already works correctly. Only change the count computation logic.

After a view is created (not updated) in CreateOrUpdateViewHandler, the creator has no privileges on the new view. Fix: auto-grant SELECT, ALTER, and DROP to the creator's roles.

Implementation:

1. Add import for `com.dremio.exec.rbac.RbacService`, `com.dremio.config.DremioConfig`, and `com.dremio.exec.rbac.MembershipStore` (for Membership).

2. Add a private helper method `autoGrantCreatorPrivileges(NamespaceKey viewPath)` that:
   a. Gets `RbacService` from `config.getContext().getRbacService()`
   b. Gets `DremioConfig` from `config.getContext().getDremioConfig()`
   c. Applies the three-way null guard: if rbacService is null OR dremioConfig is null OR RBAC is not enabled, return immediately
   d. Gets the creator username from `config.getContext().getQueryUserName()`
   e. If the user is admin (`rbacService.isAdminMember(userName)`), skip auto-grant (admin bypasses all privilege checks)

   g. IMPORTANT: Also grant to the PUBLIC role if the user has no explicit roles (so the creator always gets access). Actually, the simplest and most correct approach: find the user's FIRST explicit role (non-ADMIN, non-PUBLIC). If none exists, grant to PUBLIC. The grant is role-based (not user-based) because that's how the RBAC model works.

   Actually, the cleanest approach per the existing RBAC model: Look up the user's explicit role memberships. Grant privileges to ALL of the user's explicit roles (so if the user belongs to `analyst` and `marketing`, both roles get the grants). If the user has no explicit roles (only implicit PUBLIC), grant to PUBLIC. This ensures the creator can always access their own view.
