    Create a JUnit 5 integration test class `ITRestIcebergCatalogBranchAware` (IT prefix satisfies DremioTestcontainersUsageValidator). Uses NessieContainer for a real Nessie server.

    NOTE on class naming: The locked decision says "extend existing TestRestIcebergCatalogPlugin." This is interpreted as "extend the test suite with integration tests using the same test infrastructure pattern," NOT "add methods to the existing file." A separate class is REQUIRED because:
    1. `DremioTestcontainersUsageValidator` enforces that classes using testcontainers must have an "IT" prefix (integration test naming convention)
    2. `TestRestIcebergCatalogPlugin` is a unit test class (Test prefix) — adding testcontainer usage to it would fail the errorprone validation rule
    3. The IT class reuses the same plugin instantiation and mocking patterns from TestRestIcebergCatalogPlugin

    The test class uses a plugin-level approach: it instantiates `RestIcebergCatalogPlugin` directly (not a full Dremio server) and tests the plugin-level methods (`branchExists`, `getDatasetHandleForBranch`, `resolveVersionContext`). Full SQL-level JOIN testing (which requires a running Dremio query engine) is outside scope for this integration test — the dispatch logic was verified in unit tests (Plan 01) and by the Phase 23 architecture (per-table lookup ensures multi-table queries work by design).

    Test setup in `@BeforeAll`:

    **CRITICAL: Nessie's Iceberg REST catalog requires S3-compatible object storage (MinIO) for table operations.**

    1. Create a shared Docker network via `Network.newNetwork()`
    2. Start MinioContainer on the shared network with alias "minio"
    3. Create the "warehouse" S3 bucket in MinIO (use the AWS SDK S3 client or a simple HTTP PUT to `http://minioHost:mappedPort/warehouse`)
    4. Start NessieContainer on the shared network, configured with `withS3Warehouse("minio", 9000, minio.getS3Endpoint(), "minioadmin", "minioadmin")`
    5. Create a `RestIcebergCatalogPlugin` configured with `enableNessie=true` pointing at the Nessie container's Iceberg REST URI
    6. Use the Iceberg REST API (via a direct `RESTCatalog` client initialized with the Nessie Iceberg REST URI) to:
       a. Create a namespace "ns" on the default "main" branch
       b. Create a table "ns.table_a" on "main" with schema (id INT, name STRING)
       c. Create a branch "dev" from "main" via the Nessie REST API
       d. Create a table "ns.table_b" on "dev" (exists only on dev, not main)
       e. Create a branch with special characters: "feature/my-branch" from "main"
       f. Create a branch "release-1.0" from "main" (dot in name)
       g. Create a branch "feature branch" from "main" (spaces in name) — if Nessie rejects the branch name at creation time, skip this and document in a @Disabled test
    7. Start the plugin (calls `start()` which triggers Nessie detection)

    **MinIO bucket creation** — use the AWS SDK S3 client (already available as transitive dependency from iceberg-aws). Example:
    ```java
    S3Client s3 = S3Client.builder()
        .endpointOverride(URI.create(minio.getS3Endpoint()))
        .region(Region.US_EAST_1)
        .credentialsProvider(StaticCredentialsProvider.create(
            AwsBasicCredentials.create("minioadmin", "minioadmin")))
        .forcePathStyle(true)
        .build();
    s3.createBucket(b -> b.bucket("warehouse"));
    ```

    **Branch creation** — use raw HTTP calls via `java.net.http.HttpClient` to the Nessie REST API:
    - `GET /api/v2/trees/main` to get the hash
    - `POST /api/v2/trees` with `{"name": "dev", "type": "BRANCH"}` body + `Expected-Hash` header

    **Table creation** — use the Iceberg REST API with branch-prefixed URIs:
    - Main: `RESTCatalog` initialized with URI `http://nessieHost:port/iceberg/main`
    - Dev: `RESTCatalog` initialized with URI `http://nessieHost:port/iceberg/dev`

    **NessieContainer S3 configuration** — the `withS3Warehouse()` method sets these Nessie env vars:
    - `NESSIE_CATALOG_DEFAULT_WAREHOUSE=warehouse`
    - `NESSIE_CATALOG_WAREHOUSES__WAREHOUSE__LOCATION=s3://warehouse/`
    - `NESSIE_CATALOG_SERVICE_S3_DEFAULT_OPTIONS_ENDPOINT=http://minio:9000` (Docker-internal)
    - `NESSIE_CATALOG_SERVICE_S3_DEFAULT_OPTIONS_EXTERNAL_ENDPOINT=http://localhost:<mappedPort>` (test JVM)
    - `NESSIE_CATALOG_SERVICE_S3_DEFAULT_OPTIONS_PATH_STYLE_ACCESS=true`
    - `NESSIE_CATALOG_SERVICE_S3_DEFAULT_OPTIONS_REGION=us-east-1`
    - `NESSIE_CATALOG_SERVICE_S3_DEFAULT_OPTIONS_AUTH_TYPE=APPLICATION_GLOBAL`
    - `AWS_ACCESS_KEY_ID=minioadmin`, `AWS_SECRET_ACCESS_KEY=minioadmin`

    Test class structure:
    ```java
    @Testcontainers
    class ITRestIcebergCatalogBranchAware {
      private static final Network network = Network.newNetwork();

      @Container
      private static final MinioContainer minio = new MinioContainer()
          .withNetwork(network)
          .withNetworkAliases("minio");

      // NessieContainer must be started AFTER minio (need minio's external endpoint)
      // So we manage Nessie lifecycle manually in @BeforeAll, not via @Container
      private static NessieContainer nessie;

      private static RestIcebergCatalogPlugin plugin;

      @BeforeAll
      static void setUp() throws Exception {
        // MinIO is already started by @Container.
        // Create the warehouse bucket in MinIO.
        // Then start Nessie with S3 config pointing to MinIO.
        nessie = new NessieContainer()
            .withNetwork(network)
            .withNetworkAliases("nessie")
            .withS3Warehouse("minio", 9000, minio.getS3Endpoint(),
                MinioContainer.DEFAULT_ACCESS_KEY, MinioContainer.DEFAULT_SECRET_KEY);
        nessie.start();
        // ... create branches, tables, plugin
      }

      @AfterAll
      static void tearDown() throws Exception {
        if (plugin != null) plugin.close();
        if (nessie != null) nessie.stop();
        network.close();
      }
    }
    ```

    2. `testGetDatasetHandleForBranchDev` — Calls `plugin.getDatasetHandleForBranch("dev", entityPath("ns", "table_b"))`, asserts handle is present. This verifies a non-default branch accessor works.

    3. `testSameTableDifferentBranches` — Calls `plugin.getDatasetHandleForBranch("main", entityPath("ns", "table_a"))` and `plugin.getDatasetHandleForBranch("dev", entityPath("ns", "table_a"))`, asserts both handles are present but are DIFFERENT objects (different branch accessors). This validates no alias collision or cache interference per locked decision.

    4. `testTableExistsOnOneButNotOtherBranch` — `table_b` exists on "dev" but not "main". Calls `plugin.getDatasetHandleForBranch("main", entityPath("ns", "table_b"))`, asserts handle is empty. Calls `plugin.getDatasetHandleForBranch("dev", entityPath("ns", "table_b"))`, asserts handle is present.

    **Error handling tests:**

    5. `testBranchExistsReturnsTrueForValidBranch` — `plugin.branchExists("main")` returns true. `plugin.branchExists("dev")` returns true.

    6. `testBranchExistsReturnsFalseForNonexistentBranch` — `plugin.branchExists("nonexistent-branch")` returns false.

    7. `testBranchNotFoundErrorMessage` — This tests the expected error flow: verify that `branchExists` returns false for a nonexistent branch. The actual UserException.validationError throw happens in CatalogImpl (tested via unit test in Plan 01). Here we just validate the plugin-level branchExists behavior against a real Nessie server.

    **Special character branch name tests:**

    8. `testBranchWithSlashInName` — Calls `plugin.branchExists("feature/my-branch")`, asserts it returns true (branch was created in setup). Calls `plugin.getDatasetHandleForBranch("feature/my-branch", entityPath("ns", "table_a"))`, verifies the handle is present. This tests the locked decision for special character handling.

    9. `testBranchWithDotInName` — Calls `plugin.branchExists("release-1.0")`, asserts true. Calls `plugin.getDatasetHandleForBranch("release-1.0", entityPath("ns", "table_a"))`, verifies handle is present.

    10. `testBranchWithSpacesInName` — Calls `plugin.branchExists("feature branch")`, asserts it returns true (branch was created in setup). Calls `plugin.getDatasetHandleForBranch("feature branch", entityPath("ns", "table_a"))`, verifies the handle is present. If Nessie rejects branch names with spaces (during @BeforeAll creation), this test should be annotated with `@Disabled("Nessie does not support spaces in branch names")` and the test body should document what happened.

    **Nessie detection tests:**

    11. `testNessieDetectedOnStart` — Asserts `plugin.isNessieDetected()` is true, `plugin.getDefaultBranch()` returns "main".

    12. `testIsWrapperForSupportsBranchAwareRestCatalog` — Asserts `plugin.isWrapperFor(SupportsBranchAwareRestCatalog.class)` is true.

    **Regression and mixed-source tests:**

    13. `testEnableNessieFalseNotBranchAware` — Create a second plugin with `enableNessie=false` pointing at the same Nessie server. Assert `plugin.isWrapperFor(SupportsBranchAwareRestCatalog.class)` returns false. Close the plugin after test. This validates the locked decision for enableNessie=false regression.

    14. `testMixedSourceDispatchDifferentiation` — Validates the locked decision "Mixed-source queries must be validated" at plugin level. Creates two plugins pointing at the same Nessie server: `nessiePlugin` with `enableNessie=true` and `plainPlugin` with `enableNessie=false`. Asserts:
        - `nessiePlugin.isWrapperFor(SupportsBranchAwareRestCatalog.class)` returns `true`
        - `plainPlugin.isWrapperFor(SupportsBranchAwareRestCatalog.class)` returns `false`
        - `nessiePlugin.branchExists("main")` returns `true` (branch-aware path works)
        - `plainPlugin` has no `branchExists` method accessible via `unwrap` (confirming the non-versioned source never enters the branch-aware dispatch path)
        This proves that CatalogImpl's `isWrapperFor` check correctly differentiates which sources enter the three-way branch-aware dispatch vs the standard code path, which is the mechanism that makes mixed-source queries (JOINs between Nessie-enabled and plain sources) work correctly. Close `plainPlugin` after assertions.

    **resolveVersionContext test:**

    15. `testResolveVersionContextBranch` — Calls `plugin.resolveVersionContext(VersionContext.ofBranch("dev"))`, asserts result is `ResolvedVersionContext` with type BRANCH and refName "dev".

    16. `testResolveVersionContextNotSpecified` — Calls `plugin.resolveVersionContext(VersionContext.NOT_SPECIFIED)`, asserts result uses the default branch name "main".
