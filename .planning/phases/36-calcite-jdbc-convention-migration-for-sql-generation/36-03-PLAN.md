import org.apache.calcite.sql.SqlDialect;
import org.apache.calcite.sql.dialect.OracleSqlDialect;
import org.apache.calcite.sql.dialect.PostgresqlSqlDialect;
import org.junit.Test;
import static org.junit.Assert.*;

public class TestCalciteDialectSql {

  @Test
  public void testPostgresQuotesIdentifier() {
    SqlDialect pg = PostgresqlSqlDialect.DEFAULT;
    // quoteIdentifier wraps in dialect-appropriate quotes
    // PostgreSQL uses double-quotes
    String quoted = quoteSingle(pg, "public");
    assertTrue(quoted.contains("\"public\"") || quoted.contains("public"));
  }

  @Test
  public void testOracleQuotesIdentifier() {
    SqlDialect oracle = OracleSqlDialect.DEFAULT;
    String quoted = quoteSingle(oracle, "HR");
    assertTrue(quoted.contains("\"HR\"") || quoted.contains("HR"));
  }

  @Test
  public void testOracleDisallowsAs() {
    // OracleSqlDialect.allowsAs() returns false (protected method, verified via javap).
    // Test indirectly: build a simple JdbcRel subtree with an alias and check that
    // the rendered SQL for Oracle does NOT contain " AS " as a table alias keyword.
    // Use DremioJdbcImplementor to render a JdbcCalciteLeaf and verify the FROM clause.
    // Alternatively, simply verify that Oracle-rendered join SQL omits AS — covered
    // by integration tests in TestOracleJoinPushdown. Here, document the behavior:
    //
    // NOTE: allowsAs() is protected — cannot be called from test code directly.
    // Oracle's lack of AS is verified end-to-end by TestOracleJoinPushdown.
    // This test validates the dialect object is the expected type.
    SqlDialect oracle = OracleSqlDialect.DEFAULT;
    assertTrue(oracle instanceof OracleSqlDialect);
    // The actual allowsAs() behavior is tested via integration tests.
  }

  @Test
  public void testPostgresDialectType() {
    SqlDialect pg = PostgresqlSqlDialect.DEFAULT;
    assertTrue(pg instanceof PostgresqlSqlDialect);
    // PostgresqlSqlDialect.allowsAs() returns true (protected, cannot call directly).
    // Verified end-to-end by TestPostgresJoinPushdown which checks AS in join SQL.
  }

  @Test
  public void testEmbeddedDoubleQuoteEscaping() {
    SqlDialect pg = PostgresqlSqlDialect.DEFAULT;
    // Identifier with embedded double-quote should be escaped
    String quoted = quoteSingle(pg, "my\"table");
    // Should contain doubled double-quotes: "my""table"
    assertTrue(quoted.contains("\"\""));
  }

  private static String quoteSingle(SqlDialect dialect, String id) {
    StringBuilder buf = new StringBuilder();
    dialect.quoteIdentifier(buf, id);
    return buf.toString();
  }
}

**3. If any integration test FAILS:**

The most likely failure modes and fixes:

b) **Column aliasing difference:** Calcite's JdbcProject may produce different aliases than the manual SqlBuilder. If ResultSet column labels change, JdbcRecordReader may fail to find columns. Fix by ensuring the JdbcProject output field names match what the execution layer expects.

c) **RexNode serialization issue at plan boundary:** RexNode, RelCollation, ImmutableBitSet, AggregateCall objects exist only on JdbcScanPrel (planning node). At getPhysicalOperator() time they are used to build the JdbcRel subtree and render SQL. The SQL string (not the Calcite objects) is serialized into JdbcGroupScan. This should work because JdbcGroupScan only serializes the SQL string. If there is any issue with the Calcite objects being null or invalid at getPhysicalOperator() time, add null checks.

d) **JavaTypeFactory cast failure:** If `(JavaTypeFactory) cluster.getTypeFactory()` fails, check `PlannerCatalogImpl` or `SqlConverter` for the correct way to obtain a JavaTypeFactory. Dremio's `JavaTypeFactoryImpl` extends Calcite's `JavaTypeFactoryImpl` so the cast should succeed.

e) **JdbcAggregate InvalidRelException:** The JdbcAggregate constructor throws InvalidRelException for invalid configurations. If this happens, the AggregateCall or groupSet from the original AggregatePrel should be valid. Debug by checking the specific error message.

f) **Oracle FETCH FIRST without ORDER BY:** If Calcite renders a plain FETCH FIRST without ORDER BY on Oracle, verify that JdbcSort is created even for limit-only (no collation) cases. The sort node with empty collation + fetch should still work.

For EACH failure: diagnose root cause, fix the production code or test code as appropriate. Test LOGIC must not change. Test SCENARIOS must not change. Only the implementation details (API calls, SQL format assertions) may be adapted.
