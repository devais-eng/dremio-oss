<objective>
Create the Calcite JDBC convention foundation (JdbcCalciteLeaf, createDialect()) and migrate JdbcScanPrel single-table SQL generation from SqlBuilder to direct SqlDialect usage.

Purpose: Replace SqlBuilder.buildSql() in JdbcScanPrel.getPhysicalOperator() with direct SqlDialect identifier quoting and dialect-aware LIMIT rendering. This is a pragmatic incremental migration: existing string-based pushdown fields (whereClause, groupByClause, orderByClause, selectExprs) are kept as-is and passed through to the generated SQL, while identifier quoting and LIMIT/FETCH FIRST syntax use the Calcite SqlDialect. JdbcCalciteLeaf is created as a foundation class for a future full JdbcRel subtree migration. OracleSqlBuilder becomes dead code for single-table queries.

NOTE ON DESCOPED CRITERION: ROADMAP success criterion #5 ("~10 line kernel change in DrelTransformer") is explicitly descoped for this phase. The research document (Pattern 4, "Recommendation: Option 1") concludes that the in-place getPhysicalOperator() rewrite approach requires NO kernel change -- the pushDownJdbcQuery pipeline and RELATIONAL_PLANNING phase are untouched. The DrelTransformer hook would only be needed for a full convention-based planning approach (Option 2), which is future work. This descoping is per the user decision: "limit the intervention on core kernel part."

Output: JdbcCalciteLeaf (new foundation class), createDialect() on JdbcStoragePlugin with Oracle/PostgreSQL overrides, and a rewritten JdbcScanPrel.getPhysicalOperator() using SqlDialect.

Rewrite the `getPhysicalOperator(PhysicalPlanCreator creator)` method in `JdbcScanPrel.java` to build SQL using `SqlDialect.quoteIdentifier()` for identifier quoting and dialect-aware LIMIT rendering, replacing the current `SqlBuilder.buildSql()` call. Keep ALL existing fields, constructors, clone methods, and accessors unchanged -- only `getPhysicalOperator()` changes.

**The approach:** This is a pragmatic migration. The existing string-based pushdown fields (whereClause, groupByClause, orderByClause, selectExprs) are already correct SQL fragments with inline literals (from Phase 33's parameterization + LiteralInliner). They are passed through as-is into the generated SQL. SqlDialect replaces SqlBuilder for two specific concerns:
- Identifier quoting (schema, table, column names) via `dialect.quoteIdentifier()`
- LIMIT syntax (LIMIT N vs FETCH FIRST N ROWS ONLY) via dialect instanceof check

JdbcCalciteLeaf is NOT used here -- it is a foundation class for future migration. JdbcImplementor is NOT called. This is direct SqlDialect usage only.

**Implementation steps inside getPhysicalOperator():**

1. Resolve the plugin's SqlDialect (not SqlBuilder):
   ```java
   StoragePlugin rawPlugin = creator.getContext().getCatalogService().getSource(getPluginId().getName());
   SqlDialect dialect = (rawPlugin instanceof JdbcStoragePlugin)
       ? ((JdbcStoragePlugin) rawPlugin).createDialect()
       : PostgresqlSqlDialect.DEFAULT;
   ```

2. Build SQL string using dialect for identifier quoting and limit syntax:
   ```java
   StringBuilder sql = new StringBuilder();

   // SELECT list
   if (hasAggregation() && selectExprs != null && !selectExprs.isEmpty()) {
     sql.append("SELECT ");
     sql.append(String.join(", ", selectExprs));
   } else if (getProjectedColumns() != null && !getProjectedColumns().isEmpty()) {
     sql.append("SELECT ");
     boolean first = true;
     for (SchemaPath col : getProjectedColumns()) {
       if (!first) sql.append(", ");
       sql.append(dialect.quoteIdentifier(col.getRootSegment().getPath()));
       first = false;
     }
   } else {
     sql.append("SELECT *");
   }

   // FROM
   sql.append(" FROM ");
   sql.append(dialect.quoteIdentifier(schemaName));
   sql.append(".");
   sql.append(dialect.quoteIdentifier(tableName));

   // WHERE (stored string, already valid SQL with inline literals)
   if (whereClause != null && !whereClause.isEmpty()) {
     sql.append(" WHERE ").append(whereClause);
   }

   // GROUP BY
   if (groupByClause != null && !groupByClause.isEmpty()) {
     sql.append(" GROUP BY ").append(groupByClause);
   }

   // ORDER BY
   if (orderByClause != null && !orderByClause.isEmpty()) {
     sql.append(" ORDER BY ").append(orderByClause);
   }

   // LIMIT -- dialect-aware rendering
   if (limit != null) {
     if (dialect instanceof OracleSqlDialect) {
       sql.append(" FETCH FIRST ").append(limit).append(" ROWS ONLY");
     } else {
       sql.append(" LIMIT ").append(limit);
     }
   }
   ```

   **Identifier quoting with SqlDialect:** `dialect.quoteIdentifier(String)` returns a quoted `String`. Verify the exact method signature -- in Calcite 1.22.0 it may be `quoteIdentifier(StringBuilder, String)` (void, appends to buffer) or `quoteIdentifier(String)` (returns String). If only the StringBuilder variant exists, use:
   ```java
   private static String quoteId(SqlDialect dialect, String identifier) {
     StringBuilder buf = new StringBuilder();
     dialect.quoteIdentifier(buf, identifier);
     return buf.toString();
   }
   ```
   Add this as a private static helper method on JdbcScanPrel if needed. Use `quoteId(dialect, name)` in all the StringBuilder.append() calls above instead of `dialect.quoteIdentifier(name)`.

3. Pass `Collections.emptyList()` for bindParams to JdbcGroupScan (not `this.bindParams`) since all literals are inline in the WHERE/GROUP BY/ORDER BY strings.

4. The rest of `getPhysicalOperator()` (aggregation schema handling, full schema fetch, JdbcGroupScan construction) stays IDENTICAL -- only the SQL generation changes.

- Do NOT remove SqlBuilder import yet (keep for backward compat, still used by JdbcJoinScanPrel in plan 36-02)

**Aggregation SELECT expressions:** The stored `selectExprs` list contains strings like `COUNT(*)`, `SUM("revenue")`, `"name"`. These use double-quoted identifiers from the existing RexToSqlString. They are already correct SQL fragments. Pass them through as-is in the SELECT list.
