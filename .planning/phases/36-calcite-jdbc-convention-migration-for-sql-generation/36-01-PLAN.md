<objective>
Create the Calcite JDBC convention foundation and migrate single-table SQL generation from manual SqlBuilder to Calcite's JdbcImplementor + SqlDialect pipeline.

Purpose: Replace manual SQL string construction in JdbcScanPrel.getPhysicalOperator() with Calcite's production-grade JdbcImplementor, which renders SQL from a proper JdbcRel AST. This eliminates dialect-specific SqlBuilder subclasses, manual identifier quoting, and custom SQL composition for WHERE/projection/ORDER BY/LIMIT/aggregation -- Calcite handles all of it.

Output: JdbcCalciteLeaf (new JdbcRel leaf node), createDialect() factory method on JdbcStoragePlugin with Oracle/PostgreSQL overrides, and a fully rewritten JdbcScanPrel.getPhysicalOperator() that builds a JdbcRel subtree and renders SQL via JdbcImplementor.

**Implementation steps inside getPhysicalOperator():**

1. Resolve the plugin's SqlDialect (not SqlBuilder):
   ```java
   StoragePlugin rawPlugin = creator.getContext().getCatalogService().getSource(getPluginId().getName());
   SqlDialect dialect = (rawPlugin instanceof JdbcStoragePlugin)
       ? ((JdbcStoragePlugin) rawPlugin).createDialect()
   ```

2. Create a JdbcConvention:

3. Build the JdbcRel leaf node:
   ```java
   RelTraitSet jdbcTraitSet = getCluster().traitSet().replace(convention);
   JdbcCalciteLeaf leaf = new JdbcCalciteLeaf(getCluster(), jdbcTraitSet, getTable(), convention, schemaName, tableName);
   ```

4. Build the subtree bottom-up from the stored pushdown state. The order matters: the leaf is innermost, then filter, then project/aggregate, then sort (with limit). Use `JdbcRules.JdbcFilter`, `JdbcRules.JdbcProject`, `JdbcRules.JdbcSort`, `JdbcRules.JdbcAggregate` from `org.apache.calcite.adapter.jdbc.JdbcRules`.

   **a) WHERE clause (JdbcFilter):** If `whereClause != null`, we need to reconstruct the RexNode from the stored string. BUT: the current architecture stores WHERE as a String, not as RexNode. Reconstructing a RexNode from a SQL string is not possible without a parser. Instead, take a pragmatic approach:

   **IMPORTANT DESIGN DECISION:** Rather than reconstructing RexNodes (impossible from strings), build the SQL in a hybrid way:
   - Use JdbcImplementor for structural composition (SELECT list, FROM, JOIN, GROUP BY, ORDER BY, LIMIT/FETCH FIRST).
   - For WHERE clause, since it's already a valid SQL string with inline literals (from Phase 33's LiteralInliner or the current RexToSqlString), inject it into the rendered SQL AFTER JdbcImplementor renders the base.

   **Actually, the simplest correct approach:** Build the JdbcRel subtree for the structural parts (table scan, projection, sort, limit, aggregation) and let JdbcImplementor render those. Then, if whereClause is non-null, inject it into the rendered SQL string as a WHERE clause. This is the pragmatic migration path because the WHERE clause is already a correct SQL string.

   **Revised approach -- build SQL in stages:**
   ```java
   RelNode root = leaf;

   // Projection via JdbcProject (when not aggregation)
   if (!hasAggregation()) {
     List<SchemaPath> projCols = getProjectedColumns();
     if (projCols != null && !projCols.isEmpty()) {
       // Build RexInputRef list for projected columns
       List<RexNode> projects = new ArrayList<>();
       RelDataType leafRowType = leaf.getRowType();
       for (SchemaPath col : projCols) {
         String colName = col.getRootSegment().getPath();
         int idx = leafRowType.getFieldNames().indexOf(colName);
         if (idx >= 0) {
           projects.add(getCluster().getRexBuilder().makeInputRef(leafRowType.getFieldList().get(idx).getType(), idx));
         }
       }
       if (!projects.isEmpty()) {
         RelDataType projRowType = ...; // build from projected field types
         root = new JdbcRules.JdbcProject(getCluster(), jdbcTraitSet, root, projects, projRowType);
       }
     }
   }

   // Aggregation via JdbcAggregate
   if (hasAggregation()) {
     // ... build ImmutableBitSet for groupSet, AggregateCall list
     root = new JdbcRules.JdbcAggregate(getCluster(), jdbcTraitSet, root, groupSet, null, aggCalls);
   }

   // Sort and/or Limit via JdbcSort
   if (orderByClause != null || limit != null) {
     RelCollation collation = ...; // build from orderByClause
     RexNode fetchNode = limit != null ? getCluster().getRexBuilder().makeLiteral(limit, ...) : null;
     root = new JdbcRules.JdbcSort(getCluster(), jdbcTraitSet, root, collation, null, fetchNode);
   }
   ```

   **HOWEVER**: Reconstructing `ImmutableBitSet` for aggregation group keys, `AggregateCall` for aggregate functions, `RelCollation` for sort, and `RexNode` projections from the stored STRING fields is complex and error-prone. The stored state is STRINGS, not Calcite objects.

   **FINAL PRAGMATIC APPROACH:** Use `JdbcImplementor` ONLY for the base `SELECT * FROM "schema"."table"` rendering (via JdbcCalciteLeaf), then append the stored string clauses (WHERE, GROUP BY, ORDER BY, LIMIT) exactly as SqlBuilder does -- but using the DIALECT for LIMIT vs FETCH FIRST rendering. This gives us:
   - Calcite-rendered FROM clause with proper dialect quoting
   - Calcite dialect for LIMIT/FETCH FIRST (via `dialect.unparseOffsetFetch()` or by checking dialect type)
   - Existing string-based clauses for WHERE, GROUP BY, ORDER BY (already correct SQL)
   - Path to full Calcite migration in a future phase (when pushdown rules store RexNode instead of strings)

   **Implement as follows:**

   ```java
   // 1. Render base FROM clause via Calcite
   JavaTypeFactory typeFactory = (JavaTypeFactory) getCluster().getTypeFactory();
   JdbcImplementor implementor = new JdbcImplementor(dialect, typeFactory);
   JdbcImplementor.Result result = implementor.implement(leaf);
   // Get the base "schema"."table" identifier -- but we actually just need quoting

   // 2. Build SQL string using dialect for identifier quoting and limit syntax
   StringBuilder sql = new StringBuilder();

   // SELECT list
   if (hasAggregation() && selectExprs != null && !selectExprs.isEmpty()) {
     sql.append("SELECT ");
     sql.append(String.join(", ", selectExprs));
   } else if (getProjectedColumns() != null && !getProjectedColumns().isEmpty()) {
     sql.append("SELECT ");
     boolean first = true;
     for (SchemaPath col : getProjectedColumns()) {
       if (!first) sql.append(", ");
       sql.append(dialect.quoteIdentifier(col.getRootSegment().getPath()));
       first = false;
     }
   } else {
     sql.append("SELECT *");
   }

   // FROM
   sql.append(" FROM ");
   sql.append(dialect.quoteIdentifier(schemaName));
   sql.append(".");
   sql.append(dialect.quoteIdentifier(tableName));

   // WHERE (stored string, already valid SQL with inline literals)
   if (whereClause != null && !whereClause.isEmpty()) {
     sql.append(" WHERE ").append(whereClause);
   }

   // GROUP BY
   if (groupByClause != null && !groupByClause.isEmpty()) {
     sql.append(" GROUP BY ").append(groupByClause);
   }

   // ORDER BY
   if (orderByClause != null && !orderByClause.isEmpty()) {
     sql.append(" ORDER BY ").append(orderByClause);
   }

   // LIMIT -- use dialect awareness
   if (limit != null) {
     if (dialect instanceof OracleSqlDialect) {
       sql.append(" FETCH FIRST ").append(limit).append(" ROWS ONLY");
     } else {
       sql.append(" LIMIT ").append(limit);
     }
   }
   ```

   **Wait -- this is essentially rebuilding SqlBuilder with dialect checks.** That defeats the purpose.

   **CORRECT APPROACH:** Use `JdbcImplementor` to render the FULL SQL by building a complete JdbcRel subtree. Yes, this requires reconstructing RexNodes for filter/projection/sort/agg. The WHERE clause IS the hard part since it's stored as a string. For Phase 36:

   **Build the JdbcRel tree for parts where we have structural info (projection, sort, limit, aggregation). For WHERE clause, since we cannot reconstruct RexNode from string, use `RexLiteral` with `SqlNodeToString` to inject the WHERE as a `RexCall(SEARCH, ...)` -- NO, this is still impossible.**

   **THE ACTUAL CORRECT IMPLEMENTATION:**

   Since pushdown rules store SQL fragments as strings (not RexNodes), and reconstructing RexNodes from SQL strings is not feasible in a single phase, the correct migration for Phase 36 is:

The WHERE, GROUP BY, ORDER BY strings are passed through as-is (they are already correct SQL with inline literals from Phase 33).

   - Keep the aggregation and schema-fetch logic exactly as-is (only the SQL generation changes)

   This is the correct incremental migration: SqlBuilder is replaced by direct SqlDialect usage in JdbcScanPrel, OracleSqlBuilder override is no longer needed (dialect handles FETCH FIRST and quoting), and the path is clear for a future phase to store RexNodes on JdbcScanPrel and build full JdbcRel subtrees.
