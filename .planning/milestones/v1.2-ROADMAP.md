### 📋 v1.2 GitHub Actions Docker Distribution (Planned)

**Milestone Goal:** Automate Docker image builds of the custom Dremio OSS fork and push to AWS ECR on release tags. A `v*` tag push triggers the full pipeline: Maven build, Docker image construction, and ECR push — with versioned and `latest` tags written to the registry.

## Phase Details

### Phase 9: Maven Build in CI

**Goal:** A GitHub Actions workflow triggers on `v*` tag push, installs Java 21 with Maven cache, and produces `distribution/server/target/dremio-community-{version}.tar.gz` — verifying the tarball exists before the workflow exits.
**Requirements:** TRIG-01, TRIG-02, TRIG-03, BILD-01, BILD-02, BILD-03, BILD-04
**Depends on:** Phase 8 (v1.1 complete — RBAC and Iceberg modules present in module graph)

**Plans:**
1/1 plans complete

**Key files:**
- `.github/workflows/docker-ecr.yml` — new file; workflow definition through Maven build step only (no Docker or ECR steps)

**Success Criteria** (what must be TRUE):
1. Pushing a `v*` tag to GitHub triggers the workflow run; pushing to a branch does not
2. The workflow installs Java 21 (temurin) and Maven cache restores from a prior `~/.m2` snapshot on non-cold runs
3. The Maven build completes without enforcer failure and produces `distribution/server/target/dremio-community-{version}.tar.gz` where `{version}` matches the tag with `v` stripped
4. A post-build step lists the target directory and the tarball filename is visible in the workflow log

### Phase 10: Dockerfile Adaptation

**Goal:** The `distribution/docker/Dockerfile` is rewritten as a multi-stage build using `COPY` instead of `wget`, with `eclipse-temurin:17-jre-jammy` as the runtime base, producing a locally buildable image under 1.5GB.
**Requirements:** DOCK-01, DOCK-02, DOCK-03, DOCK-04
**Depends on:** Phase 9 (tarball produced by Maven build is the input artifact)

**Plans:** 1/1 plans complete

Plans:
- [ ] 10-01-PLAN.md — Rewrite Dockerfile as multi-stage COPY-based build with eclipse-temurin:17-jre-jammy runtime

**Key files:**
- `distribution/docker/Dockerfile` — modified; wget-based single-stage replaced by multi-stage COPY-based build

**Success Criteria** (what must be TRUE):
1. Running `docker build --build-arg TARBALL_PATH=dremio.tar.gz -f distribution/docker/Dockerfile docker-context` (with a staged tarball in `docker-context/`) completes without error on a developer machine
2. `docker images` shows the built image with a compressed size under 1.5GB
3. `docker run -p 9047:9047 {image}` starts Dremio and the container log contains `Server is up` within the expected startup window
4. The tarball layer does not appear as a distinct layer in the final image (`docker history {image}` shows no ~864MB layer in the runtime stage)

### Phase 11: ECR Authentication and Push

**Goal:** The complete end-to-end workflow is wired: a `v*` tag push runs Maven, builds the Docker image, authenticates to AWS ECR, and pushes the image with both a versioned tag and `latest` — visible in the ECR repository console.
**Requirements:** ECR-01, ECR-02, ECR-03, ECR-04
**Depends on:** Phase 10 (working Dockerfile required before wiring ECR push steps)

**Plans:** 1/1 plans complete

**Key files:**
- `.github/workflows/docker-ecr.yml` — modified; ECR authentication and Docker build-push steps appended to existing workflow

**Success Criteria** (what must be TRUE):
1. Pushing a `v*` tag triggers the full workflow and the ECR push step completes without authentication error
2. The ECR repository (created in AWS before the run) contains a new image tagged with the version string (e.g., `1.2`) after the workflow finishes
3. The same ECR repository shows a `latest` tag pointing to the same image digest as the versioned tag
4. No AWS credentials (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, ECR registry URI) appear in plain text in the workflow run log
